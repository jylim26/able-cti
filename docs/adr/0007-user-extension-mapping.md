# ADR-0007: 사용자와 내선을 분리하고 login_id로 식별한다

Status: Accepted
Date: 2026-08-18

## Context

지금까지 상담원 API의 키는 내선번호였다.

    POST /api/v1/agents/1000/login

내선번호를 상담원 식별자로 쓰고 있다. 여기서 문제가 생긴다.

> 상담원이 자리를 옮기면 식별자가 바뀌는가?

바뀌면 안 된다. 상담원은 그대로고 내선만 바뀐 것이다.
통계, 상태 이력, 이후의 WebSocket 토픽은 전부 상담원에 붙어야 하는데,
식별자가 내선번호면 자리 이동마다 이력이 끊긴다.

큐 멤버의 membername도 같은 문제다. 지금은 `PJSIP/1000`을 그대로 넣어서
AMI 이벤트만 봐서는 어느 상담원이 받았는지 알 수 없다.

## Decision

사용자와 내선을 분리한다.

| 항목 | 결정 |
|---|---|
| 사용자 식별자 | `login_id` 문자열 (예: `agent1`). API 경로와 membername에 쓴다 |
| 매핑 | `agents.extension` 컬럼 그대로, nullable. 1 사용자 : 1 내선 |
| 매핑 주체 | 관리자가 사전 매핑. 지금은 마이그레이션 시드로 대신한다 |
| 로그인 | login_id로 사용자를 찾고, 매핑된 내선으로 큐에 투입한다 |
| membername | login_id를 싣는다 |

내선이 매핑되지 않은 사용자의 로그인은 거절한다(409).

### 왜 login_id인가, agents.id가 아니라

숫자 PK를 쓰면 새 컬럼 없이 끝난다. 하지만 URL과 AMI 이벤트에서
`1`과 내선 `1000`이 나란히 보이면 헷갈린다. membername은 사람이
`queue show`로 읽는 값이라 읽히는 문자열이 낫다.

### 왜 매핑 테이블을 따로 안 만드나

`agent_extensions` 테이블로 분리하면 다중 내선, 매핑 이력으로 확장할 수 있다.
지금 그 요구가 없다. 1:1이면 컬럼 하나로 충분하다.
필요해지면 그때 테이블로 뽑는다.

## Consequences

- API 경로가 `/agents/{loginId}/...`로 바뀐다. 내선 키 경로는 없어진다.
- 큐 멤버가 `agent1 (PJSIP/1000)`처럼 보인다. AMI 이벤트의
  MemberName만으로 상담원을 식별할 수 있다.
- WebSocket 토픽(로드맵 2번)은 login_id를 키로 잡으면 된다.
- 매핑 변경 API는 없다. 개발 중에는 DB를 직접 고친다.
